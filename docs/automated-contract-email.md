# Automatic Zoho purchase confirmation — implementation candidate

Owner authorises automated email for current controlled tests and future public purchases, without activating public payments, buying credits or a subscription. Existing Mail Free account verified in the Zoho EU admin console. The integrated transactional module requires a paid plan. Zoho's published Mail usage policy excludes automated/transactional email and recommends ZeptoMail; the owner acknowledges the testing stage and requests the temporary implementation. Provider acceptance is not represented as verified recipient-inbox delivery. Replacement before public launch remains an operational requirement; no claim of a provider-approved public mail service is made.

The existing frozen PDF and account download remain independent of the email provider. The EU API adapter uses server-only OAuth (messages.CREATE), bounded token/upload/send calls, fixed SiteFit sender and the exact verified purchasing email. No browser cookies/password, new dependency, AI, tracking pixel, billing call or automatic top-up. HTML/plain template is branded and versioned; no marketing is bundled.

A private PostgreSQL ledger claims one paid, verified, unrestricted purchase, binds its existing immutable contract PDF, persists a send intent BEFORE transport and stores provider acceptance separately from historical manual delivery fields. Concurrent webhook/runner requests cannot resend; expired intents become uncertain. Definite preparation failures receive at most three automatic attempts, delayed one minute; unknown send outcomes require reconciliation, never uncontrolled retry. Payment reversal and all existing report/consent/owner/budget gates remain authoritative.

Signed payment processing uses Next.js after() to send and start the existing authorised worker immediately after acknowledging Stripe. The current cron/runner is the durable fallback. No customer GET generates reports or sends mail. A successful archived-PDF send unlocks the same fulfilment job without a manual receipt operation. The existing manual channel remains valid for historical purchases. Email status has finite failed/uncertain UX with the saved contract download and no repurchase instruction.

Activation defaults OFF in both database and environment. Required secure Local/Production names: SITEFIT_ZOHO_EMAIL_ENABLED, ZOHO_MAIL_CLIENT_ID, ZOHO_MAIL_CLIENT_SECRET, ZOHO_MAIL_REFRESH_TOKEN, ZOHO_MAIL_ACCOUNT_ID. The owner has now configured EU OAuth credentials privately; refresh and account identity were verified without exposing values. Before activation: actual same-account API capability, inbox/PDF identity, missing/expired credential behavior, concurrent duplicate suppression and protected CI/ordered migration/deployment must be verified. Tests/fixtures alone are not live delivery evidence. No genuine purchase, report or real email is dispatched by this candidate's tests.

No payment/report/AI operation or credit purchase. Production activation and actual paid-webhook automatic flow are distinct verification steps, recorded on the delivery PR after observation.
