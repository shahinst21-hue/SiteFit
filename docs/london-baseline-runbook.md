# London baseline import — Phase 5

The development importer is outside the application. Run `DATA_SOURCE_PROBES_ENABLED=true npm run import:london` with Node 24 and privately configured development Supabase credentials. It explicitly allows only the linked development project. No import occurs during a Vercel build or customer request.

Official source selections:

- [OA2021 full-resolution clipped boundaries V8](https://www.arcgis.com/sharing/rest/content/items/31dac98df61a4312991646842b147e2f): analytical polygons, not the 20m generalised visualisation product or the new alpha service.
- [Region2021 full-resolution clipped boundaries](https://www.arcgis.com/sharing/rest/content/items/faef6ad7a75943489ec673b6fdb0e77f): London E12000007.
- [OA2021 exact-fit lookup V3](https://www.arcgis.com/sharing/rest/content/items/b9ca90c10aaa4b8d9791e9859a38ca67): actual layer field is LAD22CD. London authority codes are checked against the official LAD21→RGN21 layer, not guessed from address text.
- [Nomis TS001 bulk](https://www.nomisweb.co.uk/output/census/2021/census2021-ts001.zip): the OA CSV only, Census 2021 usual residents, persons, effective 2021-03-21. Disclosure perturbation applies. Acquisition does not turn census vintage into current demand.

Transport is HTTPS with exact host/service allowlists, redirects disabled, streamed byte caps and a 60-second timeout per download. Lookup paging is capped at 40,000 rows; geographies use 100-code batches and a 200MB normalised byte cap. The temporary national ZIP is bounded at 12MB and only the named OA CSV is inflated (declared/actual maximum 80MB). Raw archives/pages are never written to disk. London statistics/polygons alone are imported; no national serving dataset, personal records or postcode candidate list.

The immutable manifest records source versions, effective/acquisition times, complete response SHA-256 chain, archive checksum, transformed CRS, importer revision, borough list and row counts. Page checksum order is borough lookup, OA exact-fit lookup pages in code order, London region, then OA boundary pages in code order. Original layers are EPSG:27700; the official API performs outSR=4326 and the importer rejects other declared CRS or projected values. PostGIS validates every resulting geometry. Publication time is null when an authoritative publication date for the selected composite release is unavailable; portal modification time must not be mislabelled as observation date.

CSV headers, quoted syntax, year, codes, integers, duplicates, borough membership and exact geography/statistics joins are checked before staging. Invalid imports never activate. Bounded privileged RPC batches load a `loading` release; count/region/release-state checks precede activation. Identical validated content reuses its UUID. A changed version/content creates a separate release; never edit/delete a ready release or silently repin an existing input. Failed loading releases are operator-reviewed; no automatic repair of historical rows.

The private local manifest at `supabase/.temp/london-baseline-manifest.json` contains only permitted release provenance/IDs and is ignored by Git. The permanent manifest lives on the private database release. No credentials appear in either. The ZIP helper is dev-only fflate 0.8.3 (patched ZIP64 parser), selected with a zero-finding audit.

Actual source issue: BFC V8 OA E00018302 has a self-touching ring. Import revision 2 explicitly opts into `postgis-makevalid-area-preserving-v1`. A new, separately tested migration extracts valid polygons from MakeValid only if the EPSG:27700 area difference is at most 0.01m²; materially altered, empty or still-invalid shapes fail. Repaired rows preserve algorithm, spatial runtime and area difference in private properties. The tested real defect changes area by approximately 3.64e-12m². This is topology normalisation with recorded limitations, never a claim of rooftop accuracy. The revision-1 partial release was marked failed and its unreferenced loading rows removed by an explicitly scoped operator transaction. No ready release was changed.

Minimal permitted London rows may be written to ignored `supabase/.temp/london-import-normalised.json` after all joins validate, solely for operator inspection if loading fails. Successful import deletes this temporary representation. It contains no raw API envelope, national records or credentials. Reviewed free official download failures have at most two attempts with bounded delay; parser/schema failures are not retried. This is an operator importer, not a durable report job or shared live response cache.

Before import inspect actual database size and the current hosting allowance; after import measure database/table/index sizes and representative GiST query plans. No storage upgrade or recurring service is authorised. If verified capacity is insufficient, keep the dependent import inactive and request owner approval while continuing independent framework work. Release version, edge ambiguity and mutation denial tests run against actual PostGIS in the fresh and hosted suites.

Capacity check on 2026-10-05: hosted database initially 21,378,739 bytes. The published [minimum Free database allowance](https://supabase.com/docs/guides/platform/database-size) is 500MB (disk and database quotas differ); no plan change is made. During loading, 7,300 features occupied a database total of 54,589,107 bytes. Final measured footprint and index plan follow in the status evidence; this is not a claim of a purchased hosting entitlement or a guarantee of future multi-release capacity.

Verified release IDs/checksums and exact source URLs are in [london-baseline-manifest.json](london-baseline-manifest.json). Hosted final database size was 129,783,475 bytes; geography including indexes 99,893,248 bytes, statistics including indexes 8,036,352 bytes. One of 26,370 geography features required the recorded repair. A representative EPSG:4326 point lookup used geography_features_gist (actual Index Scan, 0.362ms, one OA). Full inside-centroid proxy and outside-London checks passed; this is spatial plumbing evidence, not a premises benchmark or demand estimate. Future accumulated releases require another capacity review; old content must remain unchanged.
